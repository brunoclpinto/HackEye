# v26.2.4 follow-up — Notes box for reviews, remarks and fix requests

Status: shipped 2026-10-27 (no bump); worker Sonnet, planner/reviewer Opus.

Planned by Opus on 2026-10-27 from the user's request: "in hackeye lab add a freeform text box where i'll write reviewes, remarks and fix requests."

This is a Lab feature on the current version: **no bump, no wipe**. The precedent is the v26.1.14 ETA and v26.1.15 orientation follow-ups. Keeping the version also keeps the user's run `5fda5626e808` (Chest-center-0004, 0–454 s, 42 min on CPU).

## Decisions (Opus)
1. **One shared notes document for the whole Lab**, not one per recording. Remarks and fix requests often span recordings or the Lab itself. A recording and time stamp can be inserted where it matters (point 4).
2. **Storage:** `LAB_DIR/notes.json` = `{"text", "updatedAt"}`. It sits outside `runs/` and `reviews/`, so it **survives version wipes**: a fix request must not vanish on a bump. Before each save the previous file is copied to `notes.prev.json` (one generation), so an accidental clear can be undone by hand. The text is limited to 100 000 characters.
3. **API:**
   - `GET /api/notes` returns `{"text", "updatedAt"}`, or `{"text": "", "updatedAt": null}` when there is no file.
   - `PUT /api/notes` takes `{"text", "baseUpdatedAt"}`. If `baseUpdatedAt` differs from the stored `updatedAt`, the reply is **409** with `detail = {"message", "current": {text, updatedAt}}`. This stops a stale tab (phone vs Mac) from silently overwriting newer notes. `"force": true` skips the check. Text that isn't a string, or is over the limit, gives 422. An empty text is saved like any other text: the file is kept, with `"text": ""`.
   - **Export:** `GET /api/reviews/export` gains a top-level `"notes": {text, updatedAt}`, with or without `?recording=`. The reviews export is what Claude checks at the start of every Lab task, so the notes are picked up the same way.
4. **UI:** a collapsible **Notes** section at the top of `#reviewPanel`, open by default (open/closed is remembered in localStorage). It holds:
   - A plain `<textarea id="notesText">`, about 8 rows, vertically resizable. Placeholder: "Reviews, remarks, fix requests… (saved on the server, kept across versions)".
   - **⏱ Insert time** (`#notesStamp`) inserts `[<recId> @ m:ss.s · run <runId>] ` at the cursor. The run part is left out when no run is loaded; the button is disabled with no recording.
   - A status line `#notesStatus`: `Saving…` / `Saved ✓ HH:MM` / `Not saved: <reason>, retrying` / the conflict notice.
   - **Autosave** 800 ms after the last keystroke and on blur. Failed saves retry with backoff (2, 4, 8 s, then every 15 s). An unsaved edit is mirrored to localStorage `hackeye.lab.notes.draft` (wrapped in try/catch). A `beforeunload` warning fires only while a save is pending.
   - **Conflict:** on 409 a notice offers **Load theirs** (replace the box with the server text) and **Keep mine** (PUT with `force`). Nothing is overwritten without a click.
   - **Sync:** on `visibilitychange` (visible) and window `focus`, when the box has no unsaved edit, it re-GETs and refreshes, so text written on the phone shows up on the Mac.
   - The Lab's keyboard shortcuts already ignore typing in a textarea.
5. **How Claude handles the notes:** at the start of a Lab task Claude reads `notes` from the export alongside the reviews. Requests in them are folded into the work, and the done-mail lists what was addressed. **Claude never edits or clears the user's notes.** The user tidies them up.

## Tests
- **Unit** (`tests/test_lab_notes.py`): empty GET with no file; PUT then GET; `notes.prev.json` backup; 409 on a stale `baseUpdatedAt` and `force` overwrite; 422 for too long or non-string text; the export carries the notes; the notes survive a version wipe.
- **E2E** (`tests/e2e/test_notes.py`): type, wait for "Saved", reload, and the text is still there; Insert time puts `[<rec> @ ` at the cursor; a stale tab gets the conflict notice. The test **saves the user's notes through the API first and restores them afterwards** (force PUT), so the run never loses the user's text.

## Update 2026-10-27: Open issues panel above the notes
The user added to the request: "above freeform review add open issues group with subgroups as presented before in here where i can click the issues and close and comment on them to be used here, similar to reviews."

### Decisions (Opus)
6. **Catalogue in the repo, the user's state in the Lab.**
   - The issue list lives in `RnD/lab/issues.json`, maintained by Claude and versioned in git, so history is kept.
   - It has the same groups the user sees in chat and in `plans/v26.2.md`:
     - **Open issues** (`O1`–`O6`, from "Open issues carried forward")
     - **Needs your decision** (backlog `5`–`9`)
     - **Untested or technical debt** (`10`–`14`)
     - **Long-term, on hold** (`15`–`17`)
     - **Closed** (items closed earlier, with date and reason)
   - Each item has `{id, group, title, details: [lines], refs?}`, plus `status: "closed", closedAt, reason` when it was closed earlier.
   - The user's actions are stored in `LAB_DIR/issues-state.json`, keyed by issue id: `{status, closedAt, note, noteUpdatedAt}`. The file sits outside the version wipe.
   - An item's status is the user's state when there is one, otherwise the catalogue's.
7. **API:**
   - `GET /api/issues` returns `{groups: [{id, title, items: [item + status, note, closedAt, noteUpdatedAt, userChanged]}]}`.
   - `PUT /api/issues/{id}` takes `{status?: "open"|"closed", note?}` (note ≤ 4000 characters) and returns the item. An unknown id gives 404.
   - The export gains `"issues"`: every item the user has touched (closed, reopened or commented), with its catalogue text.
8. **UI:** a collapsible **Open issues (N open)** section at the top of `#reviewPanel`, above Notes.
   - Each group is a collapsible subgroup with its open count. The Closed subgroup is collapsed by default.
   - Each row shows the id badge and title. A click expands the details plus a note textarea, which autosaves like the review notes (600 ms and on blur, "saved ✓").
   - The **Close** / **Reopen** toggle moves the row between its group and Closed, optimistically, through a serial write queue. An error shows a toast and reloads.
9. **How Claude handles issues:**
   - Claude reads `issues` from the export with the reviews and notes.
   - For a closed issue, Claude moves it to "Closed" in `plans/v26.2.md` and in `issues.json` (date, plus the user's comment as the reason).
   - A comment on an open issue is a decision or request to act on.
   - When a version ships, Claude adds new known issues to `issues.json`, so the panel and the docs stay the same list.
