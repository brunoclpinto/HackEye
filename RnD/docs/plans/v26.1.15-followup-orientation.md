# v26.1.15 follow-up — camera orientation (landscape / portrait) with camera-side windows

Planned by Opus on 2026-10-22 from the user's request: "add feature to hackeye lab, need to check behaviour and detection in both portrait and landscape mode … above res selection add dropdown with landscape and portrait options … works in tandem with the position dropdown (left, center, right) … use full image when it matches the image name; left: from full left towards middle; center: middle only; right: from right side to middle … black padding when the footage res does not accommodate, do not stretch". This is a Lab feature on the current version (no bump, no wipe).

## User decisions (asked 2026-10-22)
- **Window size:** the **largest window** of the target aspect that fits the source, **scaled evenly** to the selected resolution, as today. There's no stretching. Black padding fills in where the source can't fill the target without upscaling (the existing no-upscale rule).
- **Directions:** **real directions**. The lens geometry of the original frame is kept: a left window looks left of the body's forward line, objects get their true clock positions, and the walking lane stays straight ahead.

## Footage
- **Sources:** `~/media/hackeye`: `Chest-center-0001…0008` and `Head-center-0001…0011`. Source sizes are 3840×2160 (4K) or 2704×1520 (2.7K), originally landscape.
- **Names:** `<Location>-<side>-<nnnn>`, where location is the body location (chest / head …) and side is the camera position (left / center / right).

## Decisions (Opus)
1. **New `orientation` select** (`landscape` | `portrait`) placed **above Resolution** in the analysis panel, working with the existing **Camera side** select (`sideSel`: left / center / right).
   - **Defaults:** from the recording name, `landscape` + the name's side (Chest-center → landscape, center). Camera location defaults from the name too (Chest → chest, Head → head) where the body calibration has that location.
2. **Window rule** (source pixel coords, W×H source, A = target aspect: 16:9 for landscape, 9:16 for portrait):
   - **Matched** (orientation = landscape and side = the name's side): **full frame**, exactly today's pipeline. Results must be byte-identical to today.
   - **Otherwise:** the window is the largest A-shaped window that fits, with height = H for portrait, so width = H·9/16.
     - **Placement:** `left` → window left edge at x = 0 ("from full left towards middle"); `center` → centred; `right` → window right edge at x = W.
     - **Landscape note:** in landscape the largest window is the full frame, so landscape-left / right equal the full frame (side then only affects the lane offset, as today). Record this in DECISIONS as a choice the user may revisit (alternative: shifted full-size window with black padding).
   - **Scaling:** the window is scaled **evenly** to the resolution profile's target (short side spec, stride 32, native aspect of the window, no upscaling), padded with black where needed. Never stretched.
3. **Run identity:** `orientation` and the effective window (or side, when the window depends on it) are part of the run request and the run id, so portrait and landscape runs of the same range coexist. run.json records `orientation`, `side` and `window: {x0, y0, w, h}` in source pixels plus the target input size.
4. **Geometry in collision.py:**
   - **Bearing and clock:** grid x maps back to source x (`x_src = x0 + x_win·w`), and `bearing_deg` / clock / pan use the **source** lens model (HFOV of the full source, projection as today). That gives true directions.
   - **Rows:** grid y maps back to source y (same rule), so the horizon prior / mount horizon (a fraction of the source height) and ground distances stay right. Portrait keeps the full height, so the horizon fraction is unchanged when there's no vertical padding; padding rows are excluded.
   - **Focal / depth:** focal per pixel equals the source focal times the scale factor. Depth (DA2) runs on the window image; its focal and plane fit use the window's focal and principal point (offset).
   - **Padding:** padded regions are never part of the walking region, items or depth anchors (mask them out).
   - The lane polygon and the hazards' bbox / outline stay in window-normalised coords for drawing, and hazards JSON adds `window` metadata.
5. **Lab view:**
   - **Overlays:** the video still plays the full landscape proxy. Overlays (mask, lane, outlines, boxes) for a windowed run are drawn **inside the window rectangle** on the video. Outside it the frame is dimmed, and a thin frame line marks the window. Black padding regions are shown as such.
   - **Runs list:** each entry shows orientation / side (e.g. "portrait · left").
   - **Selects:** the Orientation and Camera side selects are saved per recording like the other settings. Changing them (with an existing done run) either loads the matching run if one exists, or the next Analyse creates a new one. The "already analysed / Re-analyse" note still applies.
6. **Production note (docs only):** the production resolution 960×540 has a portrait twin, 540×960. Apple/ is not touched.
